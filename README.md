# 🛰️ Dota 2 GSI — полная спецификация протокола и защита от VAC-бана

> **Что это за файл.** Дополнение к основному README проекта (`Dota 2 Insight`). Там — архитектура и продуктовое видение, здесь — инженерный разбор одного конкретного слоя: протокола Game State Integration. Документ отвечает на два вопроса ровно один раз: что технически можно получить с порта, и как гарантированно остаться вне зоны риска по VAC/ToS.
>
> **Важная оговорка.** Valve никогда не публиковала официальную документацию GSI для Dota 2 — есть только официальный dev-wiki для CS:GO/CS2, на который ссылаются как на «тот же принцип, другие поля». Всё, что ниже про конкретные имена полей для Dota 2, восстановлено сообществом (открытые GSI-серверы на Node.js, Rust, C#, Kotlin) путём анализа реального трафика игры, а не из официального reference. Список — самый полный из доступных публично, но Valve может молча добавить или переименовать поле в любом патче. Раздел 7 объясняет, как спроектировать парсинг так, чтобы это не ломало сервис.

## 1. Как это работает и почему это безопасно на уровне архитектуры

GSI — это не API в привычном смысле (вы ничего не запрашиваете) и не хак. Это **push-канал**: клиент Dota 2 сам, при старте, читает ваш `.cfg`-файл и дальше самостоятельно отправляет HTTP POST с JSON на указанный адрес — с частотой, которую вы сами задали.

```text
   Dota 2 Client (Source 2)                 Ваш локальный сервер
          │                                          │
          │ 1. читает .cfg при старте                │
          │    (нужен флаг -gamestateintegration)    │
          │                                          │
          ├──── 2. HTTP POST JSON (state) ──────────►│  каждые throttle/buffer сек
          │                                          │
          │◄──────── 3. HTTP 200 OK ─────────────────┤  (обязателен быстрый ответ!)
          │                                          │
          ├──── 4. heartbeat, если тишина ───────────►│  раз в heartbeat сек
```

Ваш процесс никогда не читает, не открывает и не изменяет `dota2.exe` — он лишь принимает то, что игра сама решила прислать. Это ровно та причина, по которой Valve создала GSI: чтобы сторонним оверлеям и трекерам **не нужно было читать память процесса** — а значит, VAC (который ищет именно несанкционированные модификации памяти/файлов и сигнатуры чит-софта) в принципе не видит здесь предмета для анализа.

**Из этого следует главный тезис документа:** безопасность определяется не фактом использования GSI, а тем, что вы не делаете сверх него. Раздел 5 разбирает это по пунктам.

## 2. Активация: конфигурация и типичные грабли

### 2.1 Обязательный флаг запуска — самая частая причина «тишины на порту»

Начиная с патча Valve от 11 марта 2022 года, GSI выключен по умолчанию (сказывается на производительности каждый кадр), и одного `.cfg`-файла недостаточно — обязательно нужен параметр запуска. Без него интеграция просто не активируется, сколько бы правильным ни был конфиг.

Steam → Библиотека → Dota 2 → Свойства → Общие → Параметры запуска:
```
-gamestateintegration
```

Множество гайдов и примеров кода 2016–2021 годов этот шаг вообще не упоминают (тогда он не требовался). Если забыть про него в собственном README — пользователи решат, что сервер сломан, хотя всё дело в одном флаге.

### 2.2 Файл конфигурации

Актуальный путь (с подпапкой, введённой позже):
```
<Steam>/steamapps/common/dota 2 beta/game/dota/cfg/gamestate_integration/gamestate_integration_insight.cfg
```
Имя обязано начинаться с `gamestate_integration_`, суффикс — произвольный.

Полный пример со всеми директивами:
```
"Dota 2 Insight GSI Config"
{
    "uri"           "http://127.0.0.1:3000/"
    "timeout"       "5.0"
    "buffer"        "0.1"
    "throttle"      "0.1"
    "heartbeat"     "10.0"
    "data"
    {
        "provider"    "1"
        "map"         "1"
        "player"      "1"
        "hero"        "1"
        "abilities"   "1"
        "items"       "1"
        "buildings"   "1"
        "draft"       "1"
        "wearables"   "1"
    }
    "auth"
    {
        "token"       "замените-на-случайную-строку"
    }
}
```

| Директива | Назначение |
|---|---|
| `uri` | Куда слать POST. Держите `127.0.0.1`, а не `0.0.0.0` — иначе порт теоретически виден другим устройствам в той же сети |
| `timeout` | Сколько секунд клиент ждёт HTTP 200 от вашего сервера, прежде чем счесть попытку неудачной |
| `buffer` | Игра группирует несколько изменений за это окно (сек) в один POST — снижает частоту запросов |
| `throttle` | Минимальный интервал между двумя последовательными POST |
| `heartbeat` | Раз в столько секунд шлётся запрос, даже если ничего не изменилось — удобно для детекта «жив ли коннект» |
| `data{}` | Булевы флаги, какие секции JSON включать в тело запроса |
| `auth.token` | Строка, которую клиент прикладывает в каждом запросе — сверяйте на сервере, чтобы отсекать случайные/поддельные POST на этот же порт от других локальных процессов |

**Для вашего стека (FastAPI):** роут должен отвечать `200 OK` сразу после парсинга, а WebSocket-рассылку и тяжёлую логику — выполнять асинхронно уже после ответа. Если сервер не укладывается в `timeout`, клиент какое-то время будет считать эндпоинт мёртвым.

Можно завести несколько `.cfg`-файлов с разными `uri` одновременно (например, для HUD и для отдельного логгера матчей) — Dota разошлёт данные на все сразу, это штатный сценарий, не создающий рисков.

## 3. Полная карта данных: что реально можно получить с порта

Ниже — все секции, которые может прислать Dota 2, по одной на каждый флаг из `data{}`. Во время матча (не наблюдения) сервер присылает данные **сразу по вашему герою/команде**, без обёртки по игрокам. В режиме наблюдателя структура расширяется до `team2` (Radiant) / `team3` (Dire) → `player0`…`player9` (0–4 Radiant, 5–9 Dire) — подробнее в разделе 4.

### 3.1 `provider` — метаданные пакета
`name` («Dota 2»), `appid` (570), `version`, `timestamp`.

### 3.2 `map` — состояние карты и общекомандные таймеры

| Поле | Что это |
|---|---|
| `matchid` | ID матча |
| `game_time` / `clock_time` | Время с начала игры / игровые часы (могут быть отрицательными до горна) |
| `game_state` | Фаза: драфт, стратегия, до горна, игра, пауза, завершение |
| `paused` | Матч на паузе |
| `daytime` | День/ночь |
| `nightstalker_night` | Перманентная ночь от улты Night Stalker (чтобы отличать от настоящей смены дня/ночи) |
| `radiant_ward_purchase_cooldown` / `dire_ward_purchase_cooldown` | Кулдаун бесплатного командного варда |
| `roshan_state` / `roshan_state_end_seconds` | Статус Рошана и секунды до смены статуса — **готовый таймер из самой игры**, точнее ручного расчёта по формуле «8/11 минут» |
| `win_team` | Победитель, в конце матча |
| `customgamename` | Название кастомной игры, если применимо |

### 3.3 `player` — экономика и статистика
`gold`, `gold_reliable`, `gold_unreliable`, `gpm`, `xpm`, `net_worth`, `kills`, `deaths`, `assists`, `last_hits`, `denies`, `kill_streak`, `kill_list`, `hero_damage`, `wards_purchased`, `wards_placed`, `wards_destroyed`, `runes_activated`, `camps_stacked`, `support_gold_spent`, `pro_name`, `team_name`.

Этого достаточно для темпа фарма в реальном времени, сравнения net worth и счётчика стаков/вардов — без сторонних источников данных.

### 3.4 `hero` — состояние героя
`id`, `name`, `level`, `xp`, `alive`, `respawn_seconds`, `buyback_cost`, `buyback_cooldown`, `health` / `max_health` / `health_percent`, `mana` / `max_mana` / `mana_percent`, `xpos` / `ypos` (позиция **только вашего героя**), `aghanims_scepter`, `aghanims_shard`, `talent_1`…`talent_8` (по два варианта на каждом из 4 уровней талантов), и дебаффы: `silenced`, `stunned`, `disarmed`, `magicimmune`, `hexed`, `muted`, `break`, `smoked`, `has_debuff`.

Три поля `gold` + `buyback_cost` + `buyback_cooldown` — это весь калькулятор байбека без единой формулы вручную.

### 3.5 `abilities` — способности
Для каждого слота `ability0…N` (последний слот обычно — ultimate): `name`, `level`, `can_cast`, `cooldown`, `ultimate` (bool), `passive` (bool), `ability_active` (для тоглов).

### 3.6 `items` — инвентарь
Слоты: `slot0`–`slot5` (основной инвентарь), `slot6`–`slot8` (рюкзак), `stash0`–`stash5` (стеш), `teleport0` (слот телепорта), `neutral0` (слот нейтралки). На каждый слот: `name`, `purchaser` (кто из команды купил — полезно для саппортов), `can_cast`, `cooldown`, `charges`, `passive`, `contains_rune` (для бутылки).

### 3.7 `buildings` — постройки
```
dota_goodguys_tower1_top / tower2_top / tower3_top / tower4_top
dota_goodguys_tower1_mid / tower2_mid / tower3_mid                  (у мида нет tower4 — только 2 базовые башни, top/bot)
dota_goodguys_tower1_bot / tower2_bot / tower3_bot / tower4_bot
good_rax_melee_top / good_rax_range_top                              (аналогично _mid, _bot — итого 6 бараков)
dota_goodguys_fort                                                   (Трон/Ancient)
```
Для Dire — те же имена с `dota_badguys_*` / `bad_rax_*`. На каждой постройке — `health` и `max_health`.

### 3.8 `draft` — стадия пиков/банов
`activeteam`, `pick` (true = пик, false = бан), `activeteam_time_remaining`, `radiant_bonus_time`, `dire_bonus_time`; на каждую команду (`team2`/`team3`): `pick0_id`…`pick4_id`, `ban0_id`…`ban5_id` (плюс соответствующие `_class` — имя героя вместо числового id).

### 3.9 `wearables` — экипированная косметика
ID предметов внешнего вида по слотам. Нужен только для визуального кастома, не критичен для тактического HUD.

### 3.10 Служебные поля
- **`auth.token`** — эхо вашего токена в каждом запросе, для проверки подлинности источника на сервере.
- **`previously`** — предыдущие значения тех полей, что изменились в этом пакете.
- **`added`** — какие поля появились впервые именно сейчас.

Пара `added`/`previously` — готовый diff. Не нужно на каждый тик руками сравнивать полное состояние: реагируйте на конкретные изменения (например, триггерить звук ровно в момент изменения `hero.buyback_cooldown`, а не на каждый входящий POST).

⚠️ **Нюанс**: `provider` и часть `map`/`player` не переотправляются в каждом `added`-событии. Если значение нужно сразу при подключении — дождитесь первого `map.game_time` и прочитайте состояние целиком, а не полагайтесь только на `added`.

### 3.11 Пример пакета (режим игрока, сокращённо)

## 4. Что GSI НЕ отдаёт — и почему это защита от читерства, а не баг

Здесь честная игра встроена в сам протокол, а не только в то, как вы его используете:

- **Во время матча** сервер получает данные **только по вашему герою и вашей команде**. Инвентарь, кулдауны, точные HP/MP врагов — не передаются вообще, физически нечего распарсить.
- **Позиция на карте** (`xpos`/`ypos`) есть только для вашего героя — координаты юнитов в тумане войны не сливаются.
- **Полная информация по всем 10 игрокам** (структура `team2`/`team3`/`player0-9`) доступна **только в режиме наблюдателя/трансляции** — что логично: наблюдатель и так видит карту без тумана войны своими глазами, GSI просто структурирует то же самое в JSON.

Другими словами: честно используя `player`/`hero`/`items` во время обычной игры, получить то, что считалось бы читерским преимуществом (видение сквозь туман войны), невозможно — Valve уже отфильтровала это на уровне движка, до всякого GSI.

## 5. Как гарантированно не получить VAC-бан

### 5.1 Как вообще работает VAC — коротко
VAC ищет несанкционированные модификации памяти запущенного процесса и его файлов, а также известные сигнатуры чит-софта; бан выносится не мгновенно, иногда спустя дни или недели после обнаружения. То есть проверяется то, что происходит **внутри и вокруг процесса `dota2.exe`**.

### 5.2 Почему путь «чистый GSI» в принципе вне зоны риска
Ваш backend — отдельный, независимый процесс, который никогда не читает и не пишет в память `dota2.exe`, не подгружает в неё DLL, не хукает DirectX/Vulkan. Он лишь принимает HTTP-запросы, которые игра сама, по собственной инициативе, шлёт на локальный порт. С точки зрения игры и VAC это обычный исходящий сетевой запрос, а не постороннее вмешательство в процесс — анализировать здесь нечего.

### 5.3 Красные линии — то, что нельзя добавлять в этот же проект, даже если технически возможно

| Не делать | Почему это опасно |
|---|---|
| Чтение памяти процесса (`ReadProcessMemory`, Cheat Engine-подобные библиотеки, SDK для чтения энтити) | Ровно то, что ищет VAC — сигнатуры внешних читалок памяти |
| DLL-инъекции, хуки рендера (оверлеи «сквозь стены» через DirectX/Vulkan) | Прямое вмешательство в процесс — практически гарантированный бан |
| Автоматизация ввода: авто-каст, авто-фарм, скрипты передвижения через симуляцию клавиш/мыши в окно игры | Это уже классифицируется как чит, а не информационный дисплей — граница, которую сам проект в README проводит правильно |
| Функциональные `.vpk`-моды (снятие тумана войны, увеличенный радиус обзора — в отличие от чисто косметических замен) | Valve прямо запрещает `override_vpk`, дающий преимущество, в матчмейкинге |
| Разведка соперника через Steam Web API на фазе пиков/банов (любимые герои врага, винрейты, «smurf detector») | 28 февраля 2023 Valve выпустила обновление, целенаправленно заблокировавшее именно такую функциональность сторонних приложений (в первую очередь Overwolf) — доступ к профилям соперников на этапе подбора матча был закрыт, а профильные СМИ фиксировали серьёзные последствия для похожих инструментов. Это не GSI, а другой (публичный Steam Web API) механизм — но именно в компаньон-приложении легко случайно «дорасти» до такой фичи |

Текущий роадмап проекта (тайминги, байбек, фарм, Рошан) ни один из этих пунктов не задевает — весь функционал строится на данных о собственной команде через официальный push-канал. Единственное место, где стоит заранее провести границу, — Фаза 6.

### 5.4 Фаза 6 (Computer Vision) — как сделать её безопасной

Формулировка в роадмапе — «распознавание артефактов врагов при клике» — звучит рискованно, но грань очень чёткая:

- ✅ **Безопасно**: распознавать то, что и так отрисовано на экране самого игрока (клик на портрет вражеского героя открывает его текущий инвентарь на экране — CV здесь просто автоматически читает то, что человек и так видит глазами, и превращает это в структурированные данные).
- ❌ **Небезопасно**: любой анализ, который восстанавливает информацию, скрытую туманом войны; автоматизация действий по результатам распознавания (авто-клик/авто-реакция); фоновое сканирование миникарты в поисках невидимых вардов/юнитов без явного действия игрока.

Практическое правило: CV-модуль имеет право «видеть» только то, что в этот момент видно человеку, и не имеет права сам ничего нажимать.

### 5.5 Архитектура: safety и privacy by design
- Слушайте `127.0.0.1`, а не `0.0.0.0`, если доступ с другого устройства в сети не нужен специально.
- Проверяйте `auth.token` на каждый входящий POST, отбрасывайте запросы без верного токена.
- Делайте Pydantic-модели с `Optional`-полями (не строгая схема) — Valve меняет/добавляет поля без предупреждения, падение парсера от одного нового поля не должно ронять весь сервис.
- Не пересылайте сырые данные матча на внешние сервера без явного согласия пользователя — в них есть `steamid`, в том числе тиммейтов, не только автора.

### 5.6 Итог одной фразой
GSI сам по себе — на 100% в списке разрешённого Valve использования, наравне с официальной Dota Plus и десятками трансляционных/коучинговых инструментов. Риск создаёт не источник данных, а то, что вы решите с ним делать: пока вы (а) не трогаете память/файлы игры, (б) не автоматизируете ввод и (в) не показываете информацию, скрытую от игрока в его текущей роли, — вы физически вне зоны, которую Valve когда-либо ограничивала или банила.

## 6. Частые проблемы при интеграции

| Симптом | Причина | Решение |
|---|---|---|
| На порт вообще ничего не приходит | Забыт флаг `-gamestateintegration` в параметрах запуска Steam | Добавить флаг, перезапустить Steam и игру |
| Файл `.cfg` игнорируется | Файл не в той папке (гайды 2016–2020 не знают о подпапке `gamestate_integration/`) или имя не начинается с `gamestate_integration_` | Проверить точный путь `game/dota/cfg/gamestate_integration/` |
| В первые секунды после коннекта `map`/`provider` пустые | Клиент не переотправляет их в каждом `added`-событии | Дождаться первого `map.game_time`, дальше кэшировать полное состояние на сервере |
| Периодически «теряется» соединение | Сервер не укладывается в `timeout`, отвечает медленнее, чем игра готова ждать | Отвечать `200 OK` сразу, тяжёлую обработку — асинхронно после ответа |
| В спектейт-режиме JSON выглядит иначе | Во время наблюдения — полная структура `team2/team3/player0-9`, во время игры — сокращённая (сразу ваш герой) | Поддерживать оба формата отдельными Pydantic-схемами |
| Новое поле от Valve не парсится / роняет сервис | Дота обновилась, добавила ключ, GSI не документирован официально | `Optional`-поля, без строгой валидации «неизвестных» ключей |

## 7. Чек-лист перед релизом

- [ ] `-gamestateintegration` прописан в инструкции по установке для пользователя
- [ ] `.cfg` кладётся в `.../cfg/gamestate_integration/`, с уникальным `auth.token`
- [ ] Сервер слушает `127.0.0.1`, не `0.0.0.0`
- [ ] Сервер отвечает `200 OK` быстрее, чем `timeout` из конфига
- [ ] Pydantic-схемы терпимы к новым/отсутствующим полям (`Optional`, без строгой валидации)
- [ ] В кодовой базе нет ни строки, которая читает память процесса, инжектит DLL или шлёт синтетический ввод в окно игры
- [ ] Нет функций, показывающих статистику/пики соперника через Steam Web API на этапе драфта
- [ ] CV-модуль (Фаза 6) ограничен тем, что уже видно на экране игрока, без автоматизации кликов
